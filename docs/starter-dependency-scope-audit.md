# Starter Dependency Scope Audit

## Rules

| Dependency Type | Scope Strategy |
|---|---|
| Internal letool module required at runtime | Normal compile dependency. |
| Spring Boot starter required for this starter's default feature | Normal compile dependency unless the feature is explicitly documented as optional integration. |
| Optional external SDK Provider | Optional dependency plus `@ConditionalOnClass` or runtime classpath detection. |
| Annotation processor | Optional or provided; not runtime. |
| Test-only framework | Test scope. |
| Servlet/Web classes used only in web starter | Guard with web starter and web application condition. |

## Initial Findings

The first scan used:

```powershell
rg "<scope>provided</scope>|<optional>true</optional>" -g "pom.xml"
```

The scan shows broad use of `provided` and `optional` across starter modules. That does not automatically mean every entry is wrong, but it creates a starter experience risk: users may add a `letool-starter-*` dependency and still need to know which Spring Boot starter or external SDK to add manually.

## Audit Conclusion

The audited starters now distinguish required runtime dependencies, optional
integrations, provider SDKs, annotation processors, and test-only dependencies.
Provider-specific infrastructure is isolated in dedicated modules, default
runtime capabilities remain directly usable after adding the corresponding
starter, and user-replaceable integrations are guarded by classpath or bean
conditions. Future dependency changes must preserve these boundaries and pass
the verification levels documented in `docs/verification-guide.md`.
