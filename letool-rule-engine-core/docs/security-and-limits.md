# 安全与资源限制

规则源码、事实、函数扩展和诊断消息可能来自不同信任边界。core 通过白名单值模型、强类型编译、有限预算、不可变快照和依赖门禁缩小风险面，但这不等于对任意宿主扩展、部署环境或业务授权提供绝对安全保证。

## 不可信输入处理

- 源码只进入固定 DSL Lexer/Parser，不交给 JavaScript、Groovy、SpEL 或其他脚本引擎。
- 事实只接受明确 Java 类型，不反射读取 POJO，不调用任意对象转换方法。
- 路径只能访问规范化事实树，不允许方法调用、动态键、通配符或 `.class`。
- 规则函数只接收不可变 `FactValue` 和受限只读 `FunctionContext`。
- 诊断参数与基础文案均有类型、长度和控制字符边界；异常原因不自动展示。

宿主仍需负责规则读写权限、租户隔离、发布审批、来源完整性、日志访问控制和函数实现审查。

## 九项 `EngineLimits`

| 限制 | 默认值 | 主要生效阶段 | 作用 |
|------|--------|--------------|------|
| `maxSourceLength` | 16384 | 词法前 | 源码 UTF-16 代码单元上限 |
| `maxTokens` | 2048 | 词法、语义诊断 | Token 数量上限，包含 EOF；也约束语义诊断预算 |
| `maxAstDepth` | 128 | 解析 | AST 层数上限 |
| `maxFunctionCalls` | 1024 | 求值 | 单次求值函数调用次数 |
| `maxTraceNodes` | 4096 | 求值追踪 | 可保留的轨迹节点数，超出后标记截断 |
| `maxSummaryLength` | 512 | 求值追踪 | 单个值摘要的最大字符数 |
| `maxFactDepth` | 64 | 事实规范化 | 根从 1 开始的事实递归深度 |
| `maxFactNodes` | 100000 | 事实规范化 | 展开后的最终事实树节点总数 |
| `maxContainerSize` | 10000 | 事实规范化 | 单个 Map、Collection 或数组元素数 |

所有值必须是正数。引擎构建时设置的是全局上限；`EvaluationOptions.limits()` 与引擎限制逐项取较小值，因此单次调用只能收紧，不能放大。事实规范化发生在求值前，应显式使用 `RuleFacts.fromMap(source, limits)` 应用相应的事实三项预算。

## 固定硬边界

即使配置更大的 `EngineLimits`，实现还保留不能放大的结构边界，包括：Parser 与 AST 内部深度 256、单次函数签名/调用参数 256、函数目录 1024、编译产物函数依赖 1024、事实依赖 2048、编译诊断 256、类型数组嵌套 64。函数上下文元数据最多 64 项，键最长 128、值最长 4096 字符；诊断参数最多 16 项并另有限长和数值规模约束。

这些硬边界保护实现不变量，不是建议配置目标。部署时应根据真实规则规模把九项可配置预算设得更小，并通过压测确定上限。

## 禁止能力与扩展责任

core 不提供反射、脚本、进程执行、环境变量/系统属性读取、文件 IO、网络、数据库或缓存访问。函数 SPI 的设计契约同样不允许借规则求值执行这些能力；需要外部数据时，由宿主先读取并转为事实，需要业务动作时在求值之后执行。

Java 接口无法阻止一个恶意自定义函数自行持有数据库或网络客户端，因此函数注册是受信任的应用部署行为，必须代码审查。`ValueSummarizer` 和消息解析器也属于宿主信任边界；框架会限制其可观察输出，但不能证明实现内部无 IO、无泄漏或线程安全。

## 消息与原因链边界

程序判断使用稳定错误码，展示层才解析文案。不要把规则源码、完整事实、数据库异常或函数异常放入诊断参数。`ExpressionEvaluationResult.failureCause()` 仅供受控技术诊断，默认消息不会展示其 cause 文本。应用若自行记录 cause，应遵守脱敏和日志权限策略。

## 依赖门禁

core 的 Maven 运行时依赖仅为 `letool-exception-core`。架构测试扫描生产类字节码，阻止 Spring、LiteFlow、JDBC、脚本、Groovy、MyBatis、Redis 客户端、Caffeine 和旧规则包等依赖引用，并检查 `Class.forName`、反射调用、`Runtime`、`ProcessBuilder`、`System.getenv` 与 `System.getProperty` 等危险方法。

门禁是回归检测，不代替依赖树审计。新增依赖时仍要检查直接/传递依赖、方向和循环，并运行模块测试。

## 数据库边界

框架不建表，不依赖 JDBC、JPA 或 MyBatis，也不声明固定规则表结构。规则来源可以是数据库，但 repository、事务、租户、版本和发布流程属于业务层。不要在规则函数中即时查询数据库：这会破坏延迟上界、可复现性和并发治理。只有成熟的跨项目存储契约才应考虑独立的可选 repository 模块，且不得改变 core 的纯 Java 依赖边界。
